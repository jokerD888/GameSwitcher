# 2026-10-28 游戏模式卡顿回归分析与修复

> 后续状态：已根据用户要求恢复并修复模式 B。下文的“停用”保留为临时止血历史；当前实现、完整进程基线和独立恢复守护见 [模式 B 修复说明](MODE_B_FIXES.md)。

比较范围：10c0668 → 4fd85c5 → 02c7f1b。用户反馈：模式 B 后键鼠及整机交互严重卡顿，只能关机再开机；当时这台电脑是 GameViewer 控制端，正在操作其他电脑。

## 已确认的证据

- 4fd85c5 新增并推荐默认深度挂起，主路径是递归子进程 → NtSuspendProcess → EmptyWorkingSet；10c0668 没有这条路径。
- 02c7f1b 修正了 64 位句柄与 API 声明，但没有修正冻结策略、子进程保护和恢复日志问题。
- 本地操作日志显示一次模式 B 操作冻结了 3 个应用、共 29 个进程。落盘快照只有 3 个根记录，没有 tree_pids。
- 后续核对实际 baseline.json 为 []，本次 3 个挂起根目标均未命中基线或排除规则。原代码并非没有读取基线：main.py 在根目标筛选时使用了 baseline_exes；但空基线没有提供任何基线应用保护。
- “捕获基线”调用的是 visible_apps()，仅记录当前具有可见、有标题顶层窗口的应用，并不是所有开机后台进程。后台/托盘应用可能未被捕获。递归后代阶段也没有再次应用基线与排除规则；因此用户期待的“开机进程基线定向保护”并没有完整实现。
- 代码层面可复现落盘缺陷：suspend_apps() 校验时复制字典，tree_pids 写在返回的 suspended 列表中；调用方却从原始 targets 读取此字段，因而没有保存实际结果。恢复只能退回处理根 PID。
- 进入挂起前只校验根进程，递归后代没有逐个校验用户、会话、基线、排除和系统保护规则。多个可见目标存在父子重叠时，还可能重复挂起同一进程。
- 恢复忽略 NtResumeProcess 的失败结果；根恢复失败或后代仍挂起时，仍可能报告成功并清掉记录。
- 退出在设置取消标记和等待 worker 之前，同步读取快照并尝试恢复；退出与尚在进行的挂起存在竞争，还会阻塞托盘消息线程。
- 放弃恢复对旧挂起进程调用 terminate()，与“保留现场”的数据安全目标冲突，且后代只有 PID、没有创建时间。
- 对修复前 HEAD 运行已有 50 项安全测试，11 项失败。旧的 version 2 正常关闭快照也被缺省解释为 suspend，绕过原有恢复确认和去重路径。

## 为什么可能影响键鼠和整机交互

低级键鼠钩子的回调需要安装它的线程处理消息。如果控制端客户端或其他工具安装了这类钩子，冻结线程可以使输入链路等待回调超时。当前电脑是控制端，因此不能把现象简单解释为“远端电脑掉线”。是否正是某个 GameViewer 钩子导致全部本机卡顿，仍需要事发时的线程栈/跟踪数据才能证明。

此外，任意冻结桌面应用会中断窗口消息、IPC 或应用持有的锁；隐藏顶层窗口不会解除这些依赖。这种操作无法靠一个系统进程文件名名单保证对所有桌面应用安全。

EmptyWorkingSet 仅尽量移出工作集页面，并不承诺数据全部写入 SSD、内存使用变为 0 或毫秒级恢复。页面可能仍在 RAM 的 transition/cache 中，后续访问还可能发生软缺页或需要磁盘读取的硬缺页。批量裁剪是额外风险，但本次没有采集磁盘或缺页跟踪，因此不把“磁盘抖动”宣称为已证实的唯一根因。

- [LowLevelKeyboardProc：回调运行在线程消息上下文，超时处理](https://learn.microsoft.com/en-us/windows/win32/winmsg/lowlevelkeyboardproc)
- [Working Set：工作集裁剪、transition pages、软/硬缺页](https://learn.microsoft.com/en-us/windows/win32/memory/working-set)
- [Working Set Information：EmptyWorkingSet 主要用于测试和调优](https://learn.microsoft.com/en-us/windows/win32/psapi/working-set-information)

## 修复决策

本次停止提供通用“无损深度冻结”，恢复正常关闭作为默认且唯一启用的游戏模式。原因是仅修复 ctypes、延长等待、增加排除名单或隐藏窗口，都不能消除任意桌面进程冻结的依赖风险。

这里的停用是事故后的临时止血措施，并不等于证明深度挂起功能无法修复。若保留模式 B，应独立修正全量用户进程基线采集、每个候选及后代的保护规则校验、去重与身份记录、挂起/恢复事务和回滚；工作集裁剪应与挂起解耦。当前本地止血版尚未实现这套模式 B 修复，不能将停用本身表述为用户所需功能已经修复完成。

1. UI 禁用模式 B，核心 suspend_apps() 也在任何扫描、快照修改或窗口操作前拒绝调用。
2. 移除 NtSuspendProcess、EmptyWorkingSet、进程树递归冻结、窗口隐藏及裸 PID 恢复/终止操作。不会自动改动用户的页文件设置。
3. 恢复关闭前落盘、等待正常关闭、尊重存活/取消关闭的旧逻辑。默认操作类型固定为 close。
4. 旧版没有 action 字段的 version 2 快照按正常关闭解释；非法类型报错，不能回落到冻结。
5. 已结束的完整 Windows 启动周期中的旧冻结记录，转为启动记录恢复；当前周期或身份不明的记录保留，不自动碰旧 PID。
6. 针对 Windows 快速启动等导致 boot_time 没更新的情况，提供“确认已重启：恢复旧启动记录”：用户明确确认后，仍要求原进程身份已经不存在，先备份原 JSON，再转换为启动恢复。不会恢复重启前已消失的未保存内存。
7. 退出不再同步解冻；放弃恢复也不再终止进程。无法安全丢弃的当前会话旧记录会明确阻止清空。
8. 撤回 0 MB / 100% 无损 / SSD 全量置换宣传，恢复保留运行依赖的打包配置。

## 使用修复版

先退出旧版，再运行新 EXE。模式 B 会显示为停用。若关机再开机后仍显示旧挂起记录，选择“确认已重启：恢复旧启动记录”，核对提示后恢复；不需要重新打开应用则可以放弃记录。之后使用正常关闭模式。

若未保存内容只存在于旧进程内存中，关机/重启后无法由 JSON 启动记录恢复，应查看目标软件自身的自动恢复文件。
